# RDS Break-Glass Access (dev)

Direct internet access to the RDS PostgreSQL instance for debugging, data inspection, or manual migrations. Normally the RDS security group allows connections from ECS tasks only. The break-glass workflow temporarily adds a `0.0.0.0/0` ingress rule on port 5432, and removes it when you're done.

> **Always close access when finished.** The workflow reminds you, but there is no automatic expiry.

---

## How it works

| | Normal state | Break-glass open |
|---|---|---|
| RDS endpoint | Public DNS (resolves globally) | Same |
| Security group | ECS tasks only on 5432 | + `0.0.0.0/0` on 5432 |
| `publicly_accessible` | `true` (dev only) | Same |

The RDS instance is `publicly_accessible = true` in dev so it gets a resolvable public DNS name. The security group is the actual gate — nothing can connect until the break-glass rule is added.

---

## Step 1 — Open access

Go to **GitHub Actions → RDS Break-Glass → Run workflow** and select `open`.

Or via the CLI:

```bash
gh workflow run aws-rds-breakglass.yml \
  --field action=open
```

The workflow prints the RDS hostname in the job log once the rule is added.

---

## Step 2 — Fetch credentials

```bash
# RDS endpoint
aws rds describe-db-instances \
  --region eu-north-1 \
  --db-instance-identifier my-salon-dev-postgres \
  --query "DBInstances[0].Endpoint.Address" \
  --output text

# Username
aws secretsmanager get-secret-value \
  --region eu-north-1 \
  --secret-id /my-salon/dev/db-username \
  --query SecretString --output text

# Password
aws secretsmanager get-secret-value \
  --region eu-north-1 \
  --secret-id /my-salon/dev/db-password \
  --query SecretString --output text
```

All three in one block, ready to connect:

```bash
export PGHOST=$(aws rds describe-db-instances \
  --region eu-north-1 \
  --db-instance-identifier my-salon-dev-postgres \
  --query "DBInstances[0].Endpoint.Address" --output text)

export PGPASSWORD=$(aws secretsmanager get-secret-value \
  --region eu-north-1 \
  --secret-id /my-salon/dev/db-password \
  --query SecretString --output text)

psql -h "$PGHOST" -p 5432 -U salon_app -d salon
```

---

## Step 3 — Close access

Run the workflow again with `close`, or via CLI:

```bash
gh workflow run aws-rds-breakglass.yml \
  --field action=close
```

The close step is idempotent — running it when no rule exists is safe and exits cleanly.

---

## Secrets reference

All credentials are stored in AWS Secrets Manager under `/my-salon/dev/`:

| Secret path | Contents |
|---|---|
| `/my-salon/dev/db-username` | `salon_app` |
| `/my-salon/dev/db-password` | auto-generated by Terraform |
| `/my-salon/dev/db-url` | JDBC connection string (for app use) |

---

## IAM permissions required

The AWS credentials used (either your personal AWS profile or the `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` GitHub secrets) need:

```json
{
  "Effect": "Allow",
  "Action": [
    "ec2:DescribeSecurityGroups",
    "ec2:AuthorizeSecurityGroupIngress",
    "ec2:RevokeSecurityGroupIngress",
    "rds:DescribeDBInstances",
    "secretsmanager:GetSecretValue"
  ],
  "Resource": "*"
}
```

The GitHub Actions workflow uses the same `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` secrets already configured for ECS deploys. If those credentials don't yet have the EC2 / Secrets Manager permissions above, add them to the IAM user.

---

## Security notes

- `publicly_accessible = true` is set only in `dev_mode`. Production RDS is `publicly_accessible = false` and this workflow has no effect on it.
- The security group rule added by `open` is not managed by Terraform — a subsequent `terraform apply` will not remove it. Always use the `close` action to clean up.
- If you forget to close, the next `terraform apply` will not restore the rule either (Terraform only manages the ECS-to-RDS rule). Check the security group manually if unsure: `aws ec2 describe-security-groups --region eu-north-1 --filters "Name=group-name,Values=my-salon-dev-rds"`.
