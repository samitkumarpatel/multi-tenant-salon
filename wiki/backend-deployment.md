# Backend Deployment Plan — ECS Fargate + RDS

## Stack

| Layer | Technology |
|-------|-----------|
| Runtime | Java 25, Spring Boot 4.1.0, GraalVM native image |
| Container registry | GitHub Container Registry (GHCR) |
| Compute | ECS Fargate (70% Spot + 30% On-demand) |
| Load balancer | Internal ALB → API Gateway v2 (HTTPS :443) |
| Database | Amazon RDS PostgreSQL (Multi-AZ for production) |
| Secrets | AWS Secrets Manager |
| DNS | Route 53 → API Gateway custom domain |

---

## Architecture Overview

```
                        Route 53
                   api.my-saloon.online
                          │
                          ▼
              ┌─────────────────────┐
              │   API Gateway v2    │
              │   (HTTP + WS)       │
              │   VPC Link          │
              └─────────┬───────────┘
                        │
              ┌─────────▼───────────┐
              │  Internal ALB       │
              │  :80 → :8080        │
              └─────────┬───────────┘
                        │
              ┌─────────▼───────────┐
              │   ECS Service       │
              │   my-saloon-dev-api │
              │                     │
              │  70% Fargate Spot   │
              │  30% Fargate        │
              │                     │
              │  min: 1 task        │
              │  max: 5 tasks       │
              └─────────┬───────────┘
                        │
              ┌─────────▼───────────┐
              │   RDS PostgreSQL    │
              │   (default VPC)     │
              │   Single-AZ (dev)   │
              └─────────────────────┘
```

All ECS tasks and RDS run inside the default VPC. Tasks get a public IP (no NAT gateway needed) but the ALB is internal, accessible only via the API Gateway VPC Link.

## AWS Resources

### GHCR Repository

```
ghcr.io/samitkumarpatel/multi-tenant-saloon:<git-sha>
```

Images are pushed by GitHub Actions using `GITHUB_TOKEN` (no extra credentials needed for push). ECS pulls the image at task start using the GHCR pull secret stored in Secrets Manager at `/my-saloon/dev/ghcr-token`.

Populate the pull secret once before the first ECS deploy:
```bash
aws secretsmanager put-secret-value \
  --secret-id /my-saloon/dev/ghcr-token \
  --secret-string '{"username":"<github-user>","password":"<PAT with read:packages>"}'
```

### RDS PostgreSQL

| Setting | Value (dev) |
|---------|-------|
| Identifier | `my-saloon-dev-postgres` |
| Engine | PostgreSQL 17 |
| Instance class | `db.t4g.micro` (dev) / `db.t4g.small` (prod) |
| Storage | 20 GB gp3, autoscaling to 100 GB |
| Multi-AZ | No (dev) / Yes (prod) |
| Backup retention | 1 day (dev) / 7 days (prod) |
| Database name | `saloon` |
| Port | 5432 |

Credentials are auto-generated by Terraform and stored in **AWS Secrets Manager**:

```
/my-saloon/dev/db-url
  → jdbc:postgresql://<rds-host>:5432/saloon?sslmode=require
/my-saloon/dev/db-username
  → saloon_app
/my-saloon/dev/db-password
  → <generated by Terraform>
```

## Container Image Build

The project uses `spring-boot:build-image -Pnative` to produce a GraalVM native image packed into a lightweight OCI container (no JVM, ~50–80 MB). The CI workflow builds and pushes the image to ECR.

## CI/CD — GitHub Actions

```yaml
# .github/workflows/deploy-backend.yml
name: Deploy backend

on:
  push:
    branches: [main]
    paths:
      - "src/**"
      - "pom.xml"
      - ".github/workflows/deploy-backend.yml"
  workflow_dispatch:

env:
  REGISTRY: ghcr.io
  IMAGE_NAME: ${{ github.repository }}
  AWS_REGION: eu-north-1
  ECS_SERVICE: my-saloon-dev-api
  ECS_CLUSTER: my-saloon-dev-cluster
  ECS_TASK_DEFINITION: .aws/task-definition.json
  CONTAINER_NAME: api

jobs:
  build-and-deploy:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write

    steps:
      - uses: actions/checkout@v4

      - uses: graalvm/setup-graalvm@v1
        with:
          version: '25.1'
          distribution: 'graalvm'
          github-token: ${{ secrets.GITHUB_TOKEN }}
          cache: "maven"

      - name: Log in to GitHub Container Registry
        uses: docker/login-action@v3
        with:
          registry: ${{ env.REGISTRY }}
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Build and push image to GHCR
        id: build-image
        env:
          IMAGE_TAG: ${{ github.sha }}
        run: |
          ./mvnw -B spring-boot:build-image \
            -Dspring-boot.build-image.imageName=$REGISTRY/$IMAGE_NAME:$IMAGE_TAG
          docker push $REGISTRY/$IMAGE_NAME:$IMAGE_TAG
          echo "image=$REGISTRY/$IMAGE_NAME:$IMAGE_TAG" >> $GITHUB_OUTPUT

      - name: Configure AWS credentials
        uses: aws-actions/configure-aws-credentials@v4
        with:
          aws-access-key-id: ${{ secrets.AWS_ACCESS_KEY_ID }}
          aws-secret-access-key: ${{ secrets.AWS_SECRET_ACCESS_KEY }}
          aws-region: ${{ env.AWS_REGION }}

      - name: Render updated task definition
        id: task-def
        uses: aws-actions/amazon-ecs-render-task-definition@v1
        with:
          task-definition: ${{ env.ECS_TASK_DEFINITION }}
          container-name: ${{ env.CONTAINER_NAME }}
          image: ${{ steps.build-image.outputs.image }}

      - name: Deploy to ECS
        uses: aws-actions/amazon-ecs-deploy-task-definition@v2
        with:
          task-definition: ${{ steps.task-def.outputs.task-definition }}
          service: ${{ env.ECS_SERVICE }}
          cluster: ${{ env.ECS_CLUSTER }}
          wait-for-service-stability: true
```

The base task definition lives in `.aws/task-definition.json` (checked into the repo; the image field is replaced at deploy time by the `render-task-definition` action).

**GitHub secrets/variables needed:**

| Key | Type | Value |
|-----|------|-------|
| `AWS_ACCESS_KEY_ID` | Secret | IAM user access key ID |
| `AWS_SECRET_ACCESS_KEY` | Secret | IAM user secret access key |
| `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` are the only credentials needed — cluster and service names are hardcoded from the Terraform naming convention. |

## IAM Roles

### Deploy User (GitHub Actions — Access Keys)

Create a dedicated IAM user (e.g. `my-saloon-dev-ci`) and attach an inline policy:

Image push goes to GHCR via `GITHUB_TOKEN` — no AWS permissions needed for that. The IAM user only needs ECS deploy permissions:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ECSDescribe",
      "Effect": "Allow",
      "Action": [
        "ecs:DescribeServices",
        "ecs:DescribeTaskDefinition",
        "ecs:DescribeTasks",
        "ecs:ListTasks"
      ],
      "Resource": "*"
    },
    {
      "Sid": "ECSDeploy",
      "Effect": "Allow",
      "Action": ["ecs:UpdateService", "ecs:RegisterTaskDefinition"],
      "Resource": "*"
    },
    {
      "Sid": "PassRole",
      "Effect": "Allow",
      "Action": ["iam:PassRole"],
      "Resource": "arn:aws:iam::<account>:role/my-saloon-dev-api-exec-role"
    }
  ]
}
```

### ECS Task Execution Role

Role name: `my-saloon-dev-api-exec-role`

Attached policies:
- `AmazonECSTaskExecutionRolePolicy` (managed)
- Inline: `secretsmanager:GetSecretValue` on `/my-saloon/dev/*`

### ECS Task Role

Role name: `my-saloon-dev-api-task-role`

Start empty — add runtime permissions (SES, S3, etc.) as features are added.

## Known Constraints & Future Improvements

| Item | Note |
|------|------|
| Schema migrations | Flyway is enabled in production (`spring.flyway.enabled: true`). Add new schema changes as versioned files `V2__*.sql`, `V3__*.sql`, etc. |
| Database pooling | Spring Boot auto-configures HikariCP. Default pool size (10) is fine for 1–2 Fargate tasks; tune `maximum-pool-size` if scaling beyond 5 tasks. |
| Secrets rotation | Secrets Manager supports automatic rotation for RDS. Enable once the app is stable. |
| Blue/green deploys | The `amazon-ecs-deploy-task-definition` action does a rolling update by default. Switch to CodeDeploy blue/green if zero-downtime deployments are required. |
| Observability | Add AWS X-Ray tracing or OpenTelemetry SDK for distributed tracing across Spring Modulith events. |
| Private subnets | Currently using default VPC public subnets with `assign_public_ip = true`. Add a NAT Gateway and move tasks to private subnets for production hardening. |
